# Etalon and QualiaDB: next-wave architecture review

Review date: 2026-10-30. This is a proposal grounded in the current working trees, not a claim that the proposed work is implemented or faster. QualiaDB links assume its checkout is beside Etalon. The existing modernization and inference programmes retain their ownership; this document does not replace their plans.

The strongest next step is to make validated shader artifacts, prepared execution plans, resource ownership, and execution evidence agree across the two repositories. Keep Naga as the shader-language validator and translator, Etalon core as the safe GPU boundary, and QualiaDB as the owner of application semantics. Build on the existing Forge, prepared-runtime, capability, and arena implementations instead of introducing another universal framework.

**What the current work establishes**

- On Intel UHD 620, PCI `8086:5917`, driver `31.0.101.2141`, the unchanged DX12 multiview workload produced the first view's color in every active layer. Single→multi→sparse→multi→single controls separated the failure from incidental shader-cache priming. Adding an unused position input failed its own control sequence. Explicit vertex→flat-fragment transport passed the probe sequence. This establishes a useful mitigation, not a complete explanation of the driver's internal cache.
- The current Naga/HAL change implements that transport through a private paired-stage interface, gated to the observed driver. It preserves supplied WGSL and existing user bindings. Ten generated HLSL entry points passed actual DXC compilation, including scalar/struct returns, existing vertex ViewIndex inputs, mixed inputs, and an unchanged no-ViewIndex control. The rebuilt production binary passed five executing Intel DX12 multiview cases with fifteen render/readbacks, including canonical and mixed-I/O creation-order controls; two MSAA cases explicitly reported unsupported. The full required GPU suite remains the final qualification gate.
- The resident-tensor repair now stores its fixed arrays, count and generation in one safe `RwLock`, removing `UnsafeCell` and custom `unsafe impl Sync`. Buffer records are validated before replacement; poison fails closed. A supplemental actual-source harness passed all 53 included tests, including six resident tests for concurrent reloads, failed-load preservation, poison, initialization and strict zero-allocation hot reads. The inline-constant constructor also passed normal debug test-thread stacks after an initial nonconstant constructor overflowed. Full Qualia core integration testing remains pending; this small harness does not replace it.
- The coordinator recorded a Qualia core test build taking approximately 43 minutes and reaching 8.4 GiB private memory before linking failed after external cleanup removed active build artifacts. That is build-resource evidence, not a source-compilation failure or a completed test result. Concurrent heavy builds also forced paging on this 16-GiB host.
- The coordinator measured the portal WASM artifact at 14.26 MiB raw / 4.54 MiB gzip after adding diagnostics exports. The separate diagnostics build is being developed; its final size and feature isolation are not yet established. Lean builds have exposed incomplete feature gating.

The resident-substrate finding was a source-level safety issue, not a measured performance regression. The implemented read/write lock is the correctness baseline; no latency improvement is asserted. Each public call observes one complete generation, but existing search-then-subject lookups and multi-element exports span several calls and may cross generations. A future additive read-session or caller-buffered batch API can address that semantic requirement without escaping borrowed storage. If profiling justifies immutable publication, build the next bounded snapshot off the hot path, publish atomically, and pin readers until reclamation is safe. A generation counter or retrying a read after mutation is not sufficient synchronization for ordinary non-atomic Rust storage. Rust's [UnsafeCell contract](https://doc.rust-lang.org/std/cell/struct.UnsafeCell.html) explicitly preserves aliasing and data-race requirements. Do not trade the 42-MiB arena and hot zero-allocation constraints for an unbounded retirement queue.

**A shader contract that accepts both Forge output and supplied shaders**

The migration already has useful pieces. Etalon owns typed generation, schedules, tuning and manifests in [etalon-wgsl-forge](../../crates/etalon-wgsl-forge/src/lib.rs). Qualia retains application/domain operations, graph lowering and compatibility conversions in [its Forge module](../../../qualiaDB/crates/qualia-core-db/src/wgsl_forge/mod.rs) and [IR modules](../../../qualiaDB/crates/qualia-core-db/src/wgsl_forge/ir/mod.rs). This is not simply a completed re-export migration. Identify the canonical owner of each shared contract before removing either representation.

Supplied shaders are already supported: [ShaderSource](../../etalon/src/api/shader_module.rs) provides feature-gated WGSL, SPIR-V, GLSL and Naga inputs; [Device](../../etalon/src/api/device.rs) separates checked creation from explicitly unsafe trusted/passthrough entry points. Browser WebGPU accepts WGSL on its backend path. Qualia's [render compute API](../../../qualiaDB/crates/qualia-core-db/src/render/gpu/compute.rs) already accepts arbitrary supplied WGSL through checked module creation. Preserve this route. Authors should not have to rewrite existing shaders in Forge IR.

Introduce a small versioned shader-artifact contract with two origins: `Generated { generator, semantic_ir, schedule }` and `Supplied { language, source, entry_points }`. Both carry content hashes, provenance, source maps, requested features, workgroup/resource declarations and a derived interface description. Treat author metadata as claims until the validator derives or checks it. Generated source and supplied source converge on the same Naga/core validation boundary; native passthrough remains a separate explicit unsafe acceptance path. A Forge certificate must never bypass safe-boundary checks.

Keep these evidence levels distinct:

| Evidence | What it proves |
|---|---|
| Parsed / IR validated | Language and IR rules passed under the stated validator settings. |
| Device compatible | Requested features, limits, resource layouts and interfaces fit this device and pipeline. |
| Pipeline created | The selected backend/compiler accepted the actual pipeline. |
| Oracle verified | Actual outputs matched an identified reference and numerical tolerance on stated cases. |
| Profiled / tuned | Timings came from the identified clock and workload on the identified hardware. |

This distinction matters now. `validate_wgsl` uses all Naga capabilities, so it does not certify a target device. When `naga-validate` is disabled it returns a report with `naga_validated: false`. `certify_kernel` currently aliases that validation. Qualia now has an additive `generate_with_validation_via_etalon` helper returning the shader and `Option<EtalonValidationReport>` unchanged: WGSL returns its report, and native emission returns `None` because this helper runs no native compiler. The existing `generate_and_certify_via_etalon` signature remains a compatibility wrapper that discards the report. Focused source tests cover evidence preservation, native absence, compatibility and supplied WGSL; full integration execution is pending. This bounded API correction is implemented; the broader artifact/extension contract proposed above is not. Migrate consumers to check actual report fields and source identity before asserting evidence levels. Existing `CertificationManifest::naga_only` construction also needs an explicit evidence-policy audit before it can be treated as a checked certification boundary. An arbitrary supplied shader can be safely accepted without a numerical oracle; it must not be described as mathematically certified.

For extensibility, register namespaced, versioned operator schemas with typed operands/results, effects, capability requirements, bounded lowering, and optional oracle adapters. Initial registrations can be trusted build-time Rust implementations or declarative expansions into known IR operations. Unknown versions/operators fail explicitly. A supplied WGSL module remains a first-class leaf artifact. Runtime packages must not automatically load arbitrary native libraries or run arbitrary compiler/plugin code. A future sandboxed extension mechanism requires its own budgets and trust contract; it is not a prerequisite for useful extensibility.

Separate the keys for semantic artifacts, generated/translated source, compiled shader blobs, and complete pipelines. Include compiler identity/options and interface-lowering version where they affect code. Pipeline state such as view instancing belongs in the pipeline key. Do not salt every shader by view mask to mask an unexplained driver defect. The current private interface lowering gives the same shaders across view masks while leaving actual view-instancing state in the PSO.

Migration proof should include supplied/generated equivalents; malformed input; unsupported capabilities; conflicting bindings; source-map diagnostics; validation-disabled builds; unknown extension versions; and cache invalidation after compiler/driver changes. Keep a real supplied-shader corpus in the regression suite. Numerical oracles supplement these tests and do not replace validation.

**Execution, memory and hardware dispatch**

Keep the distinction already present in [accelerator types](../../crates/etalon-agent/src/accelerator/types.rs): hardware detected, runtime available, workload supported, and execution verified are separate facts. [Qualia inventory](../../../qualiaDB/crates/qualia-core-db/src/platform/accelerator_inventory/mod.rs) deliberately does not restore execution verification from discovery. Extend receipts with the operator/model hash, precision policy, runtime/compiler identity and driver/device epoch; invalidate workload verification when those change.

Use the same logical workload contract with different prepared implementations: CPU slices/SIMD, iGPU shared-memory paths where supported, dGPU resident buffers with measured staging, and NPU/DSP provider graphs only for supported operators. Do not equate a GPU adapter or installed provider with NPU/DSP execution. ONNX Runtime's [provider interface](https://onnxruntime.ai/docs/execution-providers/) assigns supported graph nodes/subgraphs; provider presence alone does not establish placement. Preserve the harness's explicit fallback policy and actual-provider evidence, including mixed-provider execution when deliberately allowed.

Reuse [geometry_workspace](../../../qualiaDB/crates/qualia-core-db/src/specialized_libs/computational_geometry/geometry_workspace.rs), [prepared-runtime budgets](../../../qualiaDB/crates/qualia-core-db/src/inference/runtime/mod.rs), and existing queue tokens. A prepared plan should own validated dimensions, bindings, memory reservations and immutable resources. Submission should consume only a bounded set of validated dynamic values. Reclamation must be owned by a completion tracker, not by the name of a lease struct. Test queue mismatch, generation reuse, cancellation, device loss and early user-handle drops. Retain validation in core; a fast path must not delegate safety to HAL.

Measure actual allocation behavior before describing `ComputeLane::submit` as zero-heap: its HAL implementation currently creates an encoder and records a compute pass. Existing buffer pools and small readbacks are useful, but comments estimating eliminated work are not a benchmark. Prefer bounded asynchronous readback slots and retained prepared resources over blocking every step. Any command-graph/capture optimization must specify dynamic bindings, resource lifetime, invalidation and fallback semantics.

**Build, browser and qualification architecture**

Use [qualia-inference-kernel](../../../qualiaDB/crates/qualia-inference-kernel/src/lib.rs), already dependency-free and `forbid(unsafe_code)`, as the extraction pattern: contracts and CPU oracles first, backend implementations next, product facades last. Preserve the 48-byte NQuin ABI and facade re-exports while moving compilation ownership. Separate crates change the dependency graph; moving files between directories within one crate does not establish that isolation.

Make product feature sets explicit and test their actual closures. Cargo features are [additive and unified](https://doc.rust-lang.org/cargo/reference/features.html), so an unrelated workspace consumer can enlarge a supposedly lean build. Prefer small product crates and additive capability features to mutually exclusive product modes in one core crate. Test the supported native/WASM combinations, disabled-provider paths, and a no-default-features baseline. Keep diagnostics exports in a thin product instead of expanding the portal by default.

Record [Cargo timing reports](https://doc.rust-lang.org/cargo/reference/timings.html), peak process memory, artifact sizes and exact feature/toolchain hashes. Measure a cold build, a warm no-change build, and a one-leaf edit separately. Use one heavy build owner per constrained host and reusable agreed profiles; package-filtered tests should reuse that graph. Artifact cleanup must check producer ownership and active-run leases before deleting anything. The observed link failure demonstrates why deleting active Cargo outputs cannot be treated as routine disk reclamation.

Keep native backend qualification, browser application integration, and conformance distinct. The retired CTS runner is documented in [conformance coverage](../conformance-coverage.md); the Qualia/VibeScript harness does not restore that coverage. Bounded diagnostics should record actual backend/provider, compiler, adapter, shader hashes, expected/actual outputs, clock source, and a finite artifact budget. Driver regressions need creation-order and shader-identity controls as well as isolated test runs. UI/email delivery and rendering tests belong to the harness, not Etalon's independent Rust tests.

**Advanced alternatives worth evaluating after the foundations**

| Candidate | When it could win | Cost and required proof |
|---|---|---|
| Shape-aware fusion, tiled attention and subgroup/cooperative-matrix schedules | A measured hot shape is limited by transfers, dispatches or memory traffic. Existing [attention code](../../crates/etalon-tensor/src/attention.rs), [Forge schedules](../../crates/etalon-wgsl-forge/src/schedule.rs) and [autotuner](../../crates/etalon-wgsl-forge/src/autotune.rs) are the starting point. | Preserve precision/error policy and capability gating. Compare warm and cold end-to-end latency, GPU time, traffic and residency. A device or global flag is insufficient proof that every shape benefits. |
| Prepared command graphs with timeline-owned residency | Repeated fixed topology spends material CPU time encoding/submitting rather than executing. | Medium/high complexity. Dynamic bindings, generation changes and cancellation need explicit invalidation. Keep a portable measured fallback and demonstrate reduced submission cost without growing unbounded caches. |
| Optional MLIR/IREE compiler route for a bounded tensor subgraph | Existing Forge lowering cannot economically exploit a particular supported target or graph transformation. | High complexity and extra toolchain/runtime cost. [IREE](https://iree.dev/developers/general/developer-overview/) separates compiler dialects/code generation from runtime HAL/task layers. Prototype one isolated subgraph behind the shader/workload contract; require differential correctness, placement evidence and a repeatable benefit before wider adoption. It does not replace Naga's untrusted graphics-shader boundary. |
| Explicit per-view draw replay | A backend genuinely lacks usable native multiview. | Extra CPU submissions/state changes and loss of native sharing. It is not preferable to the proven private scalar transport on this supported Intel device. Mesh-based alternatives do not apply to unsupported hardware. |

For each optimization, predeclare representative shapes, seeds, model/weights, precision, warmup, sample counts, clocks and memory limits. Require correctness first, then report median/p95 with dispersion and copied bytes. Include small latency-sensitive cases and large throughput cases. Synthetic timing must remain labeled synthetic. No performance improvement or universal hardware support is asserted by this review.

Recommended implementation order: finish current GPU and resident-repair integration qualification; repair the remaining completion issues; establish lean build and shader-artifact contracts; complete prepared resource ownership and evidence propagation; then select one measured bottleneck for an optimization experiment. Broad adoption depends on those results, not on the novelty of an algorithm or framework.
