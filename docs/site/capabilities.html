Architecture, extensions and evidence

More than a sensing library.

Etalon retains wgpu's graphics foundation and adds focused libraries for application execution, generated kernels, semantic records, tensors, rendering and sensing. Availability and proof differ by backend.

Generated kernels: WGSL Forge

etalon-wgsl-forge supplies typed kernel/buffer IR, schedule and workgroup descriptions, WGSL emission and Naga validation. Additional HLSL, MSL and CUDA emitters and DXC/SPIR-V tools have target-specific prerequisites. Certification utilities compare outputs with CPU oracles; adapter-keyed manifests and tuning results record declared validation/timing evidence.

A generated shader or cached manifest alone is not proof that every backend ran it. The portable demonstration checks deterministic generation and validates the resulting WGSL.

Semantic and tensor processing

48-byte NQuin records

etalon-nquin provides the explicit wire layout, field-based filtering, CPU reference operations and GPU filtering/radix-sort implementations. The browser demo checks layout and parity on the WASM CPU, and runs GPU sieve and stable radix sorting against independent CPU results, including tails, duplicates and cancelled readbacks.

Tensor execution components

etalon-tensor includes tensor views, quantization/dequantization helpers, KV layout, fused attention and top-k pipelines. CUDA and native compute integrations require their selected features and runtime. The browser suite exercises top-k, fused attention, bounded forward-arena allocation and asynchronous readback.

Rendering and browser integration

etalon-render supplies volumetric/holographic and EMF pipelines, HUD layout and explicit camera/manifold projection POD contracts. etalon-wasm supplies worker lifecycle and transport primitives, including transferable packets and shared-buffer ring contracts. Hosts still own worker creation, canvas integration and any required cross-origin isolation.

The browser rendering demonstration draws an offscreen triangle through Etalon, reads the actual pixels back, verifies them and displays that readback. It does not claim to exercise the complete volumetric/HUD stack.

Installed app and local storage

The installable test app launches the same Etalon Rust/WASM library in a standalone window. Its manifest defines the launch URL, scope and presentation. Installation does not automatically grant WebGPU or native SDK access; each API still depends on browser support, permissions and the device. Reports record actual display mode and source revision for comparison. See the W3C Web Application Manifest specification.

The service worker caches the app bundle for offline use. Separately, the Rust/WASM report store uses the origin-private file system (OPFS) to retain reports you explicitly save, with export and deletion controls. Neither feature requires standalone display mode: both can operate in ordinary browser tabs where the APIs are available. Storage belongs to the browser's origin context; installation is not a grant to read arbitrary device files. The WHATWG File System Standard defines the private file-system API.

The report store is bounded to 16 reports, 256 KiB per report and 4 MiB total; cached application assets have a separate budget. Browser quota estimates and persistence status are shown on the device test page. A persistence request can be denied, and browser grant policies differ; installation alone does not establish a grant. Granted persistence protects against automatic storage eviction, while the user can still clear site data. The WHATWG Storage Standard defines these quota, permission and persistence semantics.

Browser Bluetooth, cameras and network metadata

The device page connects to a user-selected BLE peripheral by service UUID and operates one selected GATT characteristic through Rust/WASM: explicit reads, writes of up to 512 bytes, notifications and disconnect. The browser chooser and permissions determine access. Notification retention is bounded to 32 entries. This is GATT access, not unrestricted radio discovery or MAC-address collection; see the Web Bluetooth specification.

Network evidence reports browser-exposed online state, connection type and effective bandwidth/latency estimates when available. Effective connection labels describe estimated performance, not proof of a cellular radio generation. It cannot enumerate Wi-Fi networks, SSIDs or MAC addresses. The Network Information API defines these metadata fields; support varies by browser.

Camera access is explicitly started with audio disabled. The page can list exposed cameras, select a device or facing preference, and ingest a bounded video frame in Rust/WASM. A camera label or ordinary video stream does not establish infrared sensitivity or calibrated thermal measurements. These browser device operations retain their permission and capability requirements in both tabs and installed app windows. Try device access.

Native execution and resource coordination

etalon-agent exposes accelerator/capability state, buffer regions and leases, queue completion and explicit execution lanes. Native Vulkan prepared compute avoids ordinary per-run command recording for its sealed resources. Other backends and APIs retain their own allocation and synchronization behavior.

Linux CI separately measures warmed prepared execution with a Rust allocator instrument and runs a prepared sensing correctness check. Those runs use Mesa software Vulkan; they do not certify physical GPUs or driver/OS memory allocation. Sensing providers retain their declared allocation class until their actual deployment is qualified.

Sensing as an optional layer

The portable sensing facade composes sample layout, source, uncertainty, calibration, clocks, permissions and observations with signal primitives. CPU/GPU, radio, camera and audio providers are explicit selections. Vendor DSP/NPU/SDR adapters have separate SDK, runtime and licensing requirements. Etalon does not provide QualiaDB's database, identity or permission ontologies.
